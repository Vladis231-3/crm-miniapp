## 2. P0 — критичные

### 2.1. P0-1. Клиентский `qty: 1e400` больше не валит CRM

- `backend/app/schemas.py`: у `BookingMaterialPayload.qty`/`unitPrice` появились
  границы `ge=0`, `le=1_000_000` / `le=10_000_000` и `allow_inf_nan=False`.
  JSON-литералы `1e400` и `NaN` теперь получают 422 **до** записи в БД.
- `backend/app/main.py` (`create_booking`): материалы принимаются только от персонала
  (см. 2.2), поэтому клиентский канал закрыт целиком.
- Регрессия: `backend/tests/test_audit_2026_11_13.py::test_infinite_material_qty_rejected_without_poisoning_session`
  и `::test_nan_material_qty_rejected` — сырой JSON с `1e400`/`NaN` даёт 422, после чего
  `/api/auth/session` у админа и владельца по-прежнему отвечает 200.

### 2.2. P0-2. Клиент не управляет деньгами своей записи

`create_booking` (`backend/app/main.py`), ветка роли `client`:

- цена — **только из каталога**; если услуга не найдена, цена 0 (её проставит администратор);
- `paymentSettled` принудительно `false`, `paymentType` — `cash`;
- `materials` игнорируются.

Для персонала материалы теперь валидируются в `_sync_booking_materials`:
`stockItemId` обязан существовать (иначе 400), название/единица/цена берутся **со склада**,
а не из тела запроса.

Регрессия: `::test_client_cannot_set_price_paid_or_materials` (запись за 1 ₽ с «оплачено»
и материалом 1 000 000 × 999 999 ₽ → каталожная цена, «не оплачено», материалов нет,
склад после завершения не изменился) и `::test_client_cannot_use_unknown_service_price`.

### 2.3. P0-3. Локальные `.env` и защита туннеля

Во всех пяти конфигурациях (`backend/.env`, `portable/.env`, `desktop/.env`,
`desktop/build/atmosfera-backend/_internal/.env`, `training/backend/.env`):

- `ALLOW_INSECURE_CLIENT_AUTH=false` с комментарием-обоснованием — вход только по
  подписанной Telegram initData;
- `DATABASE_SSLMODE=require` — соединение с удалённой базой по TLS
  (раньше `sslmode` не задавался и в development TLS не требовался).

Защита туннеля переписана и стала **закрытой по умолчанию**:
`scripts/assert-safe-for-tunnel.ps1` (общий гейт) + вызов из
`scripts/start_localhostrun_tunnel.cmd` и `scripts/start_pinggy_tunnel.cmd`.
Гейт учитывает переменную окружения (она приоритетнее файла, как в `config.py`),
последнее вхождение ключа, значения `1/yes/on/TRUE`, кавычки и отсутствие `.env`
(нет доказуемо безопасной конфигурации → блок). Проверено: `false` → exit 0,
`1`/`yes` → exit 1 с сообщением.

`.env.example` дополнен `DATABASE_SSLMODE=require` и `FORWARDED_ALLOW_IPS` (см. 3.1).

## 3. P1 — высокие

### 3.1. P1-4. Rate limit: `X-Forwarded-For` больше не доверенный

- `Dockerfile`: из CMD убран `--forwarded-allow-ips "*"` (любой клиент мог подделать
  заголовок и обойти лимит на `/api/auth/staff/link` и `/api/contact`). Осталось
  `--proxy-headers`; адрес доверенного прокси задаётся переменной `FORWARDED_ALLOW_IPS`
  (по умолчанию `127.0.0.1`), она задокументирована в `backend/.env.example`.
- `_request_ip` по-прежнему предпочитает прямой адрес клиента.

### 3.2. P1-5. Код привязки Telegram

`backend/app/telegram_linking.py`:

- счётчики попыток перенесены из памяти процесса в `app_settings`
  (ключ `telegram_link_code_attempts`): рестарт и второй воркер больше не обнуляют лимит;
- серия неверных попыток **гасит выданные коды** (per-chat лимит 5/10 мин, общий
  предохранитель — 20 неверных попыток за окно);
- при перепривязке аккаунта прежний держатель получает Telegram-уведомление
  (`_notify_previous_holder`, ленивый импорт бота — цикл импортов сохранён).

### 3.3. P1-6. Зависимости

- `requirements.txt` (его ставит Vercel) синхронизирован с актуальными пинами:
  fastapi 0.141.1, starlette 1.6.0, python-multipart 0.0.31, python-dotenv 1.2.2,
  urllib3 2.7.0.
- `backend/requirements.txt`: неразрешимый `urllib3>=2.8.0` заменён на `urllib3==2.7.0`
  (версии 2.8.0 не существует — из-за этого аудит и не смог проверить файл).
- `pip install --dry-run` (офлайн), `pip check` и импорт приложения — чисто.
  `pip-audit` без сети не запускался; CI-job `ci.yml` теперь разрешим.

### 3.4. P1-7. Оплата до завершения пересчитывается

`update_booking`: при переходе в `completed` оплаченной записи вклады копилки и
pending-доли владельцев сверяются с текущим сплитом
(`_reconcile_piggy_for_booking` / `_reconcile_owner_shares_for_booking`).
Сценарий аудита (1000 ₽ → оплата → цена 2000 ₽ → завершение) даёт мастер 600,
копилка 480, владельцы 920 — распределено 2000 ₽.
Регрессия: `::test_early_payment_is_recalculated_on_completion`.

### 3.5. P1-8. Хвост доп-услуги больше не теряется

`_booking_money_split`: остаток доп-услуги, который раньше «висел нераспределённым»
(владельцы выключены или их процент < 100 %, а копилка не «весь остаток»), уходит в
копилку этого же допа — и в классическом, и в конвейерном порядке шагов.
Три существующих теста `test_money_matrix` обновлены под новый инвариант
(мастер + копилка + владельцы == чек) и получили проверку суммы.

### 3.6. P1-9. Месяцы депозитов

`_deposit_month_key` — сортировка и сравнение месяцев по (год, месяц), а не по строке
`«MM.YYYY»`. С января 2027 порядок и остатки на начало месяца считаются верно.
Регрессия: `::test_deposit_months_are_ordered_by_date` (11.2026/12.2026/01.2027 →
остатки 0/1000/3000).

### 3.7. P1-10. Серверные границы для персонала

- `schemas.py`: `BookingCreateRequest.price`, `BookingUpdateRequest.price`,
  `AddBookingServiceRequest.price`, `BookingWorkerPayload.fixedAmount`,
  `AdditionalServiceWorkerPayload.fixedAmount` — `ge=0`, `le=10_000_000`;
- `_compute_master`: фикс мастера ограничен базой сплита (суммарно по всем фиксам),
  поэтому 50 000 ₽ на записи в 1000 ₽ дают мастеру 1000 ₽, а не больше чека.
Регрессия: `::test_negative_money_rejected`, `::test_worker_fixed_cannot_exceed_check`.

### 3.8. P1-11. XSS в `training/frontend`

- `StudioInfo.tsx` больше не вставляет текст из админки как HTML — рендер по строкам,
  файл побайтово совпадает с проверенной версией основного фронтенда;
- `api.ts`: подставной `VITE_MOCK_INIT_DATA` работает только при `import.meta.env.DEV`.
Сборку `training/frontend` в этой сессии прогнать не удалось: песочница запрещает
esbuild спавнить дочерний процесс (`spawn EPERM`) — ограничение окружения, не кода.

## 4. P2 — средние

### Сделано

- **P2-12. Вход «создателя».** `config.py`: захардкоженного Telegram id больше нет,
  пустой `CREATOR_TELEGRAM_IDS` = предпросмотр ролей выключен. Исправлен `TypeError`
  в `_read_role_preview` (aware `_now()` минус naive-timestamp), из-за которого
  предпросмотр всегда был пуст. Регрессия: `::test_role_preview_ttl_handles_naive_timestamp`.
- **P2-13. Депозиты.** Мойка в уже закрытый месяц отклоняется (400); копейки
  округляются до рубля один раз и одинаково для выручки и списания; будущий месяц
  закрыть нельзя. Мойки вне абонемента (тариф `per_wash` и сверх лимита плана
  `washes`) — платная выручка: их сплит (копилка + доли владельцев) проводится
  сразу при записи, а не теряется до закрытия месяца.
- **P2-14. Зарплаты.** Операции `/api/payroll/entries` получили поле `segment`;
  выплата ложится в тот сегмент (wash/detailing), где мастер реально заработал —
  как `pay-salary` (премии/авансы/удержания остаются в «мойке»: это расход
  компании, инвариант all = wash + detailing сохранён). Ручная сумма мастера
  (`override_earned`) теперь везде трактуется одинаково — как в сплите: заменяет
  основную услугу, доп-услуги идут сверху (раньше зарплата обрезала допы).
  Добавлен сторож повторной выплаты без `clientRequestId` (та же выплата тем же
  сотрудником в течение минуты — replay).
- **P2-15. Ручной сплит.** Проверка «мастера + копилка + владельцы ≤ чек» до любых
  мутаций; сумма материалов пишется только в расход на материалы (раньше — во все
  расходы записи); `round()` заменён на `money_int` (half-up).
- **P2-16. Конкурентность.** В денежные пути добавлены пессимистичные блокировки
  строк (`SELECT … FOR UPDATE` на Postgres; на SQLite — no-op): проведение записи,
  вклады копилки, доли владельцев, списание мойки с депозита, закрытие месяца,
  выплата владельцу. Плюс сторож повторных выплат из P2-14.
- **P2-17. Права.** Выплаты долей владельцев и их детализация — только владельцу;
  доп-услуги записи больше не правит бухгалтер; админ/бухгалтер не проводят выплаты
  и авансы сверх остатка мастера.
- **P2-18. Сессия.** Debug-эндпоинты больше не принимают initData в query string
  (токен попадал в access-логи прокси).
- **P2-19. Секреты.** `.dockerignore`/`.vercelignore` исключают `.env*` (кроме
  `.env.example`) и `*.env.bak`; `.gitignore`: `!.env.example` больше не перекрывается
  правилом `.env*`.
- **P2-20. Vercel/экспорт/секреты.** «Сегодня» и границы дня считаются в бизнес-
  таймзоне (`APP_TIMEZONE`, по умолчанию Europe/Moscow) — зарплатные операции,
  месяцы депозитов и окна отчётов больше не сдвигаются на 3 часа на UTC-сервере.
  Токены календарей и client_secret в `app_settings` шифруются (Fernet, ключ из
  `APP_SECRET`; старые значения читаются и перешифровываются при записи).
  Ссылки-приглашения в календарь получили TTL 24 ч и остаются одноразовыми.
  Суммы в xlsx считаются через Decimal (`_money2`) вместо float+`round()`;
  от формул нейтрализуются сводные листы депозитов, метрики и название компании. Строка подключения к БД
  вырезается из уведомлений об ошибках. Проверено: outbox — транзакционный,
  TG-сообщения уходят только после commit (находка не подтвердилась).

### Осталось — только то, что меняет учётную политику (нужен ответ владельца)

- **P2-13 (абонплата).** Сейчас месячная абонплата с депозитного баланса не списывается,
  а закрытие месяца возвращает на баланс стоимость включённых моек. Это связанная пара:
  либо «абонплата списывается при закрытии и возврата нет», либо текущая схема.
  Любой вариант ретроспективно меняет балансы действующих абонентов — нужен выбор.
- **P2-14 (снапшот).** Начисления в ЗП считаются по ТЕКУЩИМ настройкам услуги, а не по
  замороженному на завершении снапшоту. Это осознанное решение в коде: штрафы по
  жалобам должны уменьшать уже заработанное. Переход на снапшот сделает историю
  выплат стабильной, но отключит влияние штрафов на прошлые записи — выбор владельца.
- **P2-14 (оклад «за всё время»).** Период «все» начисляет оклад только за текущий
  месяц: у сотрудников нет даты найма, и начислять «с начала времён» нельзя без неё.
  Правильное решение — добавить дату найма в карточку сотрудника (миграция + UI).
- **P2-16 (уникальные индексы).** Блокировки строк добавлены; уникальные индексы на
  `owner_profit_shares(booking_id, owner_id)` и вклады требуют миграции и разбора
  возможных дублей в боевой базе — отдельная задача.

## 5. Низкие

- `/docs`, `/redoc`, `/openapi.json` выключаются в production (`settings.is_production`).
- CSP: из `script-src` убран `'unsafe-inline'` (в сборке фронтенда нет inline-скриптов).
- Не-ASCII заголовок в cron/webhook больше не роняет `hmac.compare_digest` с 500:
  добавлен `security.secure_equals` (сравнение байтов UTF-8), применён в cron-роутере
  и в webhook/сбросе базы.
- Из git удалены `flip_push_permission.py` (снимал запрет `git push` у агента),
  `_distill_*.py`, `__dream_query*.py`, `_*_excerpt.txt` (12 файлов, нигде не
  используются, восстанавливаются из истории).
- `.gitignore`: `.env.example` снова не игнорируется.
- Доли владельцев без явных весов делятся поровну между ВСЕМИ активными владельцами
  (раньше третий и следующие молча получали 0).
- Сумма процентов мастеров 100 % больше не даёт +1 ₽ сверх базы (остаток срезается
  с текущей доли при раздельном округлении).
- В сервисном режиме с одним мастером штраф по жалобам теперь уменьшает выплату
  пропорционально снижению процента.
- Смена услуги без явной цены больше не теряет стоимость доп-услуг (каталожная цена
  складывается с их суммой).

## 8. Что нужно от владельца

1. **Ротация секретов.** `backend/.env.bak` и `training/backend/.env.bak` содержат
   **уникальные** значения `TELEGRAM_BOT_TOKEN` (46 симв.) и `APP_SECRET` (32 симв.) —
   они не дублируются в актуальных `.env`. Отозвать токен у BotFather, сменить
   `APP_SECRET`, удалить `.bak`. Перевыпустить оба `VERCEL_OIDC_TOKEN`.
2. **Пароль базы.** Если копии `.env` (в т.ч. портативная сборка) покидали машину —
   сменить пароль Supabase. База боевая: 1037 записей, 746 клиентов, 28 сотрудников.
3. **FORWARDED_ALLOW_IPS** на платформе: указать IP/сеть реверс-прокси, иначе
   rate-limit будет считать всех клиентов одним адресом прокси.
4. **Решения по P2** (депозиты сверх лимита, учётная политика ЗП, уникальные индексы).
5. Локальный вход клиента теперь требует настоящей initData: для отладки в браузере
   используйте dev-мок фронтенда, а не `ALLOW_INSECURE_CLIENT_AUTH=true`
   (гейт туннеля всё равно заблокирует публикацию).
